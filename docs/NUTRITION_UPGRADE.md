# 行食记 0.5.0 营养功能升级与设备验收

本修订包使用由部署者配置的独立持久化数据目录。本文升级参数须替换为部署环境的实际绝对路径；新包构建和部署入口见根目录 README。身体资料改为单页表单，主要操作为“让AI根据资料制定计划”和“发布身体资料”。发布始终归属实际当天，同日只保留最新资料，不再提供历史版本切换；日历日期下的“身体资料”可打开当天卡片。期望周速率由当前体重、期望体重和期望日期计算。

新计划由模型结合身体资料及结构化权威参考分析活动、热量调整和脂肪比例，再由程序复算热量、蛋白质、脂肪与碳水。知识卡保留适用人群、参考含义、原文定位和研究局限；AI需返回选值依据、差异与风险，用户确认后使用。原来的减脂−15%/0等盈亏白名单及脂肪20%～30%硬门槛已从新版身体资料计划入口移除，参考范围不冒充统一安全上限。BMI仅为体重参考，不作为制定计划的门槛；蛋白质固定按当前体重乘以适用知识范围的最低系数计算，不再由模型自由选值。训练资料为选填，不再要求用户填写总活动档位、逐项资料日期或复核。计划确认后才生效，自动调参继续关闭。只保留当前一份计划，所有日期均使用当前计划；再次保存即替换。同步日志及旧备份读取保留，用于数据兼容。主卡仅展示碳水、蛋白质、脂肪，膳食纤维放入更多营养；超过计划限额标红，热量显示“还可以吃”或“已超量”。这些计划限额不等于医学安全上限。

## 升级

校验失败时，页面、服务器窗口和账号JSON诊断日志会显示具体字段与拒绝原因；参数校验错误会显示模型返回值及未满足的校验条件。模型自动重试也会收到实际拒绝原因，不再把业务规则错误统一当成JSON格式错误。保留格式、引用真实性和数值一致性检查，以及既有1000kcal自动工具下界、10000kcal存储上界；它们不表示每个人的医学最低/最高需要量。未新增5000kcal、20%或500kcal的统一营养硬门槛。普通成人年龄和特殊情境的既有覆盖边界保持。

1. 将ZIP与同名.sha256文件一起保存，核对ZIP的SHA-256。解压到新的程序目录，保留旧目录。新包不含账号、个人数据、.env或模型。
2. 在手机设置中导出本机备份，保留待同步记录；停止旧服务。将本修订包解压到新的目录，不在已有配置的程序目录内覆盖。在新目录CMD执行（旧程序路径按当前实际使用的程序目录填写）：

```cmd
node.exe scripts\check-nutrition-runtime.mjs --verify-only
node.exe scripts\upgrade-from.mjs "<旧程序绝对路径>" --data-dir "<持久化数据目录绝对路径>"
```

第一条命令只检查运行包和知识库的完整性，不搬数据。

**已经使用固定数据目录时**：不需要再次迁移数据。数据目录设置保存在旧程序的`.env`配置中，新解压的运行包不含这份个人配置，因此新程序还需要取得相同的配置。第二条命令会读取旧配置，确认其`DATA_DIR`已经是所指定的数据目录，在固定目录保存升级前快照，再为新程序写入`.env`，保留模型、端口、账号模式和公网设置。此分支直接使用原来的固定数据目录，不重新复制数据库。`--data-dir`用于核对新程序应使用的位置，并不表示每次都会搬迁。

**第一次从旧程序目录迁往固定数据目录时**：第二条命令才会执行下面的数据复制流程。新旧目录参数都必须写完整绝对路径，不能只写文件夹名。

首次迁移时，脚本检查所有账号数据库，使用SQLite备份API复制包含WAL已提交记录的完整数据库、库身份和其他正式文件，复核后才把新.env切到指定的数据目录。旧数据原件不删除。目标目录如已有另一套数据，工具停止，不覆盖或自动合并。临时复制失败会保留暂存资料，目标和新配置不被当成成功；数据已提交而配置未完成时，同一命令可以续办。

之后各版本都使用这一个固定目录；原.env已指向它时只复用数据、保存升级前快照和新配置，不再来回搬库。模型、端口、账号模式和公网设置保留。TLS文件若原来放在旧程序目录中，也会保存到固定目录并更新路径。

固定目录内的backups/upgrade-编号保存已核验的升级前快照，.upgrade-recovery/编号保存迁移凭据与恢复配置。这些配置含服务设置或密钥，按正式数据保护，不要上传分享。UPGRADE-RECEIPT.json只存路径与校验值。回退不再读取旧目录里的.env或备份。

首次启动将旧日记库升级到SQLite结构2；手机本机结构2、服务器JSON备份2、本机JSON备份3及旧备份读取规则保留。
3. 运行START-SERVER.cmd，保持窗口打开。核对原账号、日记、照片和目标后，程序正常运行不再依赖旧程序目录，可删除旧程序目录；其中如果另放了其他个人文件，先自行保留。迁移后不要再启动保留迁移前数据副本的旧服务。新服务每天自动保存完整快照。已有 HTTPS 代理继续转发到所配置的后端端口；使用其他代理方案时按实际部署配置。浏览器刷新并等待离线资源更新后，核对设置显示0.5.0；已有日记应可直接查看，无须补高级资料。

新安装才将.env.example复制为.env并填写实际配置；已有安装使用升级脚本，不重新注册代替迁移。

## 在部署电脑按顺序检查

先检查服务，不先运行模型：

```cmd
node.exe scripts\check-local-service.mjs http://127.0.0.1:4318/api/health
node.exe scripts\check-nutrition-runtime.mjs
```

第二条只在新的.cache目录创建虚构记录，不打开DATA_DIR、不调用Ollama、不下载模型。它验证42组冻结资料、24个问答检索、生成与确认、同请求重试、同步、导出导入、重开和本机规则接口时延；生成result.json供核对。公网时延不由本机时延推断。

本机健康与0.5.0版本通过后，检查真实Ollama。先运行少量合成比较：

```cmd
node.exe --env-file=.env scripts\check-nutrition-model.mjs --profiles 3 --questions 3
```

如需完整组，用`--all`替代数量参数。完整组会产生较多模型请求；脚本打印进度并逐项保存结果，中止仍保留已完成结果。不下载模型，不读取真实日记；默认使用.env中的模型与Ollama地址。比较的是旧版提示复现、检索后模型自由生成、规则计算加受控解释三条路线。这些旧阶段比较脚本仍是隔离实验；当前产品使用身体资料分析接口，不能用旧阶段分数代替新版计划验收。结果记录每项耗时、实际调用次数、失败类型、对批准起点的数值一致性、引用ID及待人工核对的正文；数值一致不等于医学有效，来源存在不等于支持整句话。首个请求耗时不证明模型确实从显存卸载状态启动。真实模型的要点选择与引用支持关系仍须人工抽查，不能只看自动指标。

再检查原HTTPS入口：未登录只看登录页，登录原账号后核对旧日记和目标；用手机蜂窝网络分别检查登录、日记、图片和营养问答。将“本机服务”“Ollama”“公网/手机”结果分开反馈，勿把其中一项通过写成全部通过。反馈result.json即可；不要发送.env、账号库、登录令牌或个人备份。

## 手机与iOS验收

网页/PWA：已保存目标及必要依据断网重开可见；离线新增一餐，联网后只同步一次；保存计划后，过去与未来日期均使用新计划，不再选择生效日期或保存历史计划。发布身体资料后在日历日期下打开卡片；修改后再次发布，当天展示最新资料，不再显示历史版本。确认BMI超出旧区间仍能制定计划，训练留空时不编造训练。

iOS工程资源可以在Windows同步，但Xcode编译、签名、安装、Keychain/SQLite持久化、照片权限、分享与Safari缓存均需Mac及iPhone实测。工程版本为0.5.0、构建号50，使用项目已配置的HTTPS后端。Windows资源同步不等于已生成可安装IPA。

## 回退

旧0.4.3不能直接写入升级后的库。若仅模型解释失败，规则目标、记餐与手动目标仍可使用，应先保留现状定位。若必须回退，先停服、导出手机待同步备份并保留升级后新库，然后在0.5.0目录执行：

```cmd
node.exe scripts\prepare-rollback.mjs --new-data "D:\小卡回退数据_新目录" --config-output "D:\小卡回退配置.env"
```

两个目标必须不存在。工具读取固定数据目录中的恢复配置与快照，并检查旧程序是否支持该快照结构；只复制到新目录，更换同步epoch，不覆盖现有新库，不启动服务。回退使用升级前快照，升级后的新增记录仍在保留的新库/手机备份中，不会自动合并进旧版。若快照已是结构2，而旧程序不能支持，工具拒绝回退，需使用支持结构2的修复版。

回退数据准备不要求旧程序目录仍存在。要实际运行旧版，若已删旧目录，需要重新解压兼容的旧运行包；在该旧程序目录执行：

```cmd
node.exe --env-file="D:\小卡回退配置.env" server\index.mjs
```

核对原账号、旧日记与新的同步epoch。新版手机本机待处理记录继续保留；遇到协议不兼容时先恢复兼容服务，不清空缓存或强行上传。不要把旧数据库直接覆盖新库，也不要用旧程序尝试修改新库。

本包的真实固定电脑模型、公网、iPhone结果由实际执行后填写；发布包中的开发机检查不能代替这些验收。
